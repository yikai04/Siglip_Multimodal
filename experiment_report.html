Key Finding: Loss Function Bug

Critical Discovery

The original repo_v2/loss.py had a sign error compared to the working version. This caused training loss to be ~200x higher (204 vs 6.2 at epoch 1) and made the model nearly unable to learn.

Difference

- logits = -t * logits + b # WRONG sign convention - loss = labels * logits # WRONG sign convention + logits = t * logits + b # CORRECT, matches SigLIP paper + loss = -labels * logits # CORRECT, matches SigLIP paper

After fixing this, loss dropped from 204 to 6.2 at epoch 1, and the model became trainable again.

Key Code: CosineWarmupScheduler

class CosineWarmupScheduler(torch.optim.lr_scheduler.LambdaLR): def __init__(self, optimizer, warmup_steps, total_steps, base_lr, min_lr_ratio=0.01): def lr_lambda(step): if step < warmup_steps: return step / max(1, warmup_steps) progress = (step - warmup_steps) / max(1, total_steps - warmup_steps) decay = 0.5 * (1 + math.cos(math.pi * progress)) return min_lr_ratio + (1 - min_lr_ratio) * decay # LR decays to min_lr, NOT to 0 super().__init__(optimizer, lr_lambda)

Test Result

t2i_R@1=29.83%, i2t_R@1=32.07%

Improvement vs baseline: +8.57% t2i_R@1, +11.19% i2t_R@1

Experiment 5: Wider ResNet + ColorJitter (Current Best)

Configuration

  • ResNet-18 width=48 (vs 32 in previous experiments)
  • LR: Cosine+warmup (warmup_ratio=0.1, min_lr_ratio=0.01)
  • Augmentation: Resize(224) + RandomHorizontalFlip + ColorJitter(brightness=0.2, contrast=0.2, saturation=0.2, hue=0.1)
  • Epochs: 100, Batch: 256
  • Model: ResNet-18 (width=48) + Transformer (2 layers, 4 heads, embed_dim=256)

Why Wider ResNet Helps

ResNet-18 with width=48 has ~1.5x more parameters (4.4M vs 2.9M) than width=32. On Flickr8k, this additional capacity allows the image encoder to capture more visual features, improving retrieval accuracy. The model still fits comfortably on the RTX 4090 (17GB VRAM).

Why ColorJitter Helps (Mildly)

ColorJitter(brightness=0.2, contrast=0.2, saturation=0.2, hue=0.1) provides mild color augmentation without destroying image content like RandomResizedCrop did. This teaches the model to be invariant to color variations, making embeddings more robust.

Experiment 6: Wider + EMA (decay=0.999)

Configuration

  • Same as Exp5 but with EMA (decay=0.999)
  • EMA is only applied at final test evaluation, not during validation
  • Validation uses original model throughout training

EMA Implementation

class ModelEMA: def __init__(self, model, decay=0.999): self.decay = decay self.shadow = copy.deepcopy(model).cpu() # EMA weights on CPU def update(self, model): for p_ema, p_model in zip(self.shadow.parameters(), model.parameters()): p_ema.data.mul_(self.decay).add_(p_model.data.cpu(), alpha=1.0 - self.decay)

EMA Analysis

The EMA model completely failed — it produced near-random results. This is because with decay=0.999, the shadow weights are dominated by the early (poorly trained) model weights. Even after 12600 steps, the EMA hasn't converged to the well-trained model. This shows that EMA with high decay is not suitable for this training setup where the model weights change rapidly. The original model's test result (36.65%) slightly outperformed Exp5 (35.86%), likely due to random variation between runs.

Experiment 7: Deeper Transformer + Larger Embed (Killed)

Configuration

  • ResNet-18 width=48
  • Transformer: 4 layers, 8 heads, embed_dim=512
  • Epochs: 100 (killed at epoch 21)

Why Killed

  • Training was significantly slower (~3s/it vs ~2.5s/it)
  • At epoch 21, t2i_R@1 was only ~15%, far behind Exp5's trajectory
  • Larger model on small Flickr8k dataset poses overfitting risk
  • The marginal benefit of model capacity is limited on 30k training pairs

Conclusion

Flickr8k is too small for a 4-layer, 512-dim Transformer. The added capacity doesn't help because the dataset can't support it. Keep model small (2 layers, 256 dim) and focus on training strategies instead.

Experiment 8: Best Config + 200 Epochs (Overfitted)

Configuration

  • ResNet-18 width=48, Transformer: 2 layers, 4 heads, embed_dim=256
  • LR: Cosine+warmup (warmup_ratio=0.1, min_lr_ratio=0.01)
  • Augmentation: Resize+Flip+ColorJitter
  • Epochs: 200 (killed at epoch 97)
  • Total steps: 25200, Warmup steps: 2520

Result: Overfitted

Val R@1 plateaued at ~30% around epoch 90 and started declining. Val loss kept increasing from epoch 50 onwards. Training was killed at epoch 97.

This shows that 100 epochs is the sweet spot for this model on Flickr8k. Training longer leads to overfitting, not improvement.

RandAugment is far too aggressive for Flickr8k. The automated augmentation strategy applies strong transformations (rotation, shearing, posterization, etc.) that destroy semantic content critical for image-text matching. Experiment 15: Gradient Accumulation (Effective Batch=128)

Configuration

  • Same as Exp6 but with grad_accum=2 (effective batch size = 64×2 = 128)
  • Epochs: 100

Test Result

t2i_R@1=29.56%, i2t_R@1=31.91%

WORSE — -7.09% t2i_R@1 vs Exp6

Conclusion

Larger effective batch size didn't help. With batch_size=64, each batch already contains enough negatives for contrastive learning. Doubling the effective batch reduces the number of optimizer steps per epoch (505 → 252), which means less gradient updates over the same number of epochs. The LR scheduler bug (total_steps not accounting for grad_accum) also contributed to suboptimal scheduling.

Why Cosine + Warmup Wins

Comparison: Constant LR vs Cosine LR

With constant LR, the model uses the same learning rate throughout training. This leads to:

  • Early epochs: learning rate is too high relative to the model's capability, causing instability
  • Late epochs: learning rate is too low relative to the remaining gap, slowing convergence

Cosine annealing with warmup addresses both issues:

  • Warmup (10% of total): Gradually increases LR from 0 to base_lr, preventing early instability
  • Cosine decay: Smoothly decreases LR, allowing fine-tuned adjustments in later epochs
  • Min LR floor (1% of base): Prevents LR from hitting 0, so the model continues learning even at the end

The Bug: LR Decaying to 0

The original CosineWarmupScheduler used 0.5 * (1 + cos(pi * progress)) which decays LR to 0 at the end. This means the last ~10-20% of training is essentially wasted. The fix adds a floor: min_lr_ratio + (1 - min_lr_ratio) * decay.
